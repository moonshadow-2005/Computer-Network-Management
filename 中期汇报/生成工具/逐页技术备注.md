#### 可能追问与回答

1. **你们到底做了什么，和实验环境自带的工具有什么区别？**
   环境提供设备、访问条件和 ping/iperf3 等工具；我们实现了采集调度、数据保存、有效性判断、五项管理逻辑、网页交互、授权入口和部署脚本。工具输出经过处理后能持续保存、查询和追溯，不只是手工执行几条命令。

2. **这是静态网页，还是有真实后端？**
   是有真实后端的系统。网页通过 `/api/v1` 查询 DEV 上的数据库；后台轮询会继续产生新观测。展示层是原生网页，并不等于数据是静态写死的。

3. **项目用的哪些技术是自己实现的？**
   业务规则、API、前端、部署与本机网关由项目实现；SNMP 采集器实现了本项目需要的 BER 编解码及 GET/GETNEXT/GETBULK 子集。FastAPI、Uvicorn、SQLite、操作系统 ping 和 iperf3 是使用的基础组件，不能说这些工具也是自己开发的。

4. **目前是演示数据还是真实数据？**
   本地样例模式与真实环境分开。此 PPT 的网页截图访问的是 DEV，采样记录标为 `live`；设备清单中仍可能保留 `document` 来源，因为登记清单来自课程文档。某一页面出现多种来源不等于所有内容都是模拟数据。

5. **完成度是多少？**
   不用未经定义的百分比。可以回答“五项功能都有实现、真实采集链路已打通，但全部业务流量归属、安全检测深度和若干现场恢复案例仍未完成”。具体边界见第 3、13 页。

6. **你负责哪部分，其他同学负责什么？**
   沿用开题分工：蒋天乐负责整体方案、后端与集成；金海负责故障/配置及相关采集；元泽瑞负责性能/流量统计；段景瀚负责安全与公共界面。若问某段代码的具体作者，应依据实际提交与组内工作记录回答，不能把计划分工直接当成每段代码的作者证明。

#### 本页数字的准确含义

**先纠正一个容易说错的地方：8 是“登记候选对象”，不是 8 个接口；48 才是当前接口表的记录数。**

| 对象 ID | 访问地址 | 登记角色 | 当前如何观测 |
|---|---|---|---|
| `dev` | `192.168.0.100` | 开发/部署主机 | 运行管理服务；当前周期采集不把它作为普通 SNMP/ping 目标 |
| `r-0-1` | `192.168.0.1` | 路由候选地址 | SNMP 读取接口、路由、地址与计数器 |
| `r-0-2` | `192.168.0.2` | 路由候选地址 | 同上 |
| `r-0-5` | `192.168.0.5` | 路由候选地址 | 同上 |
| `r-0-8` | `192.168.0.8` | 路由候选地址 | 同上 |
| `host-1` | `192.168.1.1` | 子网 1 测试主机地址 | DEV 发起 ping；允许参与已配置的 iperf3 任务 |
| `host-2` | `192.168.2.1` | 子网 2 测试主机地址 | DEV 发起 ping；允许参与已配置的 iperf3 任务 |
| `host-3` | `192.168.3.1` | 子网 3 测试主机地址 | DEV 发起 ping；当前未配置网页测速所需的专用 SSH 授权 |

**48 条接口记录的组成：4 个路由候选地址 × 每个地址返回 12 个接口索引。** 2026-11-15 01:32（北京时间）的补充只读核对中，四个候选的索引与名称均如下：

| ifIndex | 接口名称 | 说明 |
|---|---|---|
| 1 | `lo` | 回环接口，可有多个地址；不是外部网线端口 |
| 2 | `ens3` | 实际系统接口名；具体业务角色需结合地址与路由核实 |
| 3 | `ens4` | 同上 |
| 4 | `ens5` | 同上 |
| 5 | `ens6` | 同上 |
| 6 | `ens7` | 同上 |
| 7 | `ens8` | 同上 |
| 8 | `ens9` | 同上 |
| 9 | `ens10` | 同上 |
| 10 | `ens11` | 同上 |
| 11 | `ens12` | 同上 |
| 12 | `virbr0` | 虚拟网桥名称；其用途及业务影响尚未独立确认 |

接口主键是 `设备ID:ifIndex`。例如 `r-0-1:3` 是候选 `192.168.0.1` 返回的索引 3，即 `ens4`；`r-0-8:7` 是候选 `192.168.0.8` 返回的索引 7，即 `ens8`。

| 概览数字 | 应怎样解释 |
|---|---|
| 8 | 已登记的候选/管理对象数，不是全网自动扫描发现的物理设备总数 |
| 48 | 按候选分别保存的接口记录，包含回环和虚拟接口 |
| 92 | 当前保留的路由记录；已有实测为四个候选各 23 条，不是 92 条物理链路 |
| 4 条活跃故障 | 四个候选的 `:12 / virbr0` 接口状态异常记录，不等于四台设备宕机 |
| 3 条待处理风险 | `open` 状态风险；另有 1 条已确认，因此未解除风险合计 4 条 |

#### 可能追问与回答

1. **为什么叫候选，不能直接说四台路由器吗？**
   课程给出的是访问地址；多个地址可能属于同一节点的不同接口，也可能是不同实例。我们有不同 sysName 和地址表等观测，但没有把这些当作独立物理身份的最终证明，因此系统不自动归并，也不宣称完成物理去重。

2. **48 条接口就是 48 个独立物理网口吗？**
   不是。一方面包括 `lo`、`virbr0` 等逻辑接口；另一方面当前按访问候选保存记录，没有完成物理实例去重。准确说法是“48 条被观测接口记录”。

3. **三台测试主机和四个路由候选一定是七台不同机器吗？**
   不能保证。补充核对中，`192.168.1.1` 也出现在 `r-0-1:6 / ens7` 的 SNMP 地址表中。它说明登记角色与地址观测存在关联，不能据此直接断言独立主机数量、地址冲突或完整物理结构；需要课程侧身份确认。

4. **同样叫 ens4，业务角色就相同吗？**
   不一定。当前 `.0.1/.0.2/.0.5` 管理地址分别出现在各自 `ens4` 上，但 `.0.8` 出现在 `r-0-8:7 / ens8` 上。接口名是对象内部的名字，不能凭名称给所有对象统一指定业务角色。

5. **为什么设备表的 host 显示“课程文档”，但 ping 是“真实采集”？**
   设备登记信息与测量记录是不同数据层。主机地址来自课程文档，后续 ping 样本独立标记为 `live`；来源需要按记录判断。

6. **每 30 秒刷新，是不是每 30 秒采集一次？**
   不是。30 秒是浏览器读数据的自动刷新周期；后台采集按自己的调度执行，关闭浏览器也会运行。具体采样周期看第 5 页。

7. **设备数为什么没有随着运行时间一直增加？接口数为什么不等于地址数？**
   当前目标是固定登记清单，采集更新已有对象，不做全网扫描。一个接口可以没有 IPv4 地址，也可以有多个 IPv4 地址，所以接口数 48、地址记录 27、设备候选 8 没有一一对应关系。

8. **数据库健康正常，能证明网络正常吗？**
   不能。health 的 `database=ok` 说明相应数据库检查可通过；采集是否成功、样本是否有效和业务是否正常，要分别看采集轮次、原始观测与实际业务证据。

#### 架构与端口速查

```text
浏览器
  → Windows 127.0.0.1:8000：本机授权网关
  → Windows 127.0.0.1:18080：SSH 本地转发
  → SSH 加密通道：通过本机 WARP SOCKS5 127.0.0.1:40000 接入
```

#### 可能追问与回答

1. **网页、采集器和数据库分别在哪台机器？**
   浏览器在维护电脑；网页资源、API、后台采集器与 SQLite 在 DEV。Windows 的本机网关负责接入和附加授权，不在本机代替 DEV 采集内网。

2. **为什么本机 8000 和 DEV 8000 不冲突？**
   它们属于不同机器的回环地址。另用本机 18080 区分内部 SSH 转发与对浏览器开放的本机授权入口。

3. **WARP 是系统业务的一部分吗？必须每台电脑都安装吗？**
   它是这台新电脑当前采用的课程接入方式，不是网络管理业务模块。若另一台电脑本来能直接连接课程 IPv6 SSH，可以走直连；本机启动器支持核对直连条件。WARP 连上也不代表 SSH、授权和 DEV 服务都已经正常。

4. **关闭浏览器或维护电脑，后台会停吗？**
   不会因此停止 DEV 上的 systemd 服务与轮询；本机断开只影响这台电脑的访问。DEV 服务停止或实验网异常则是另一回事。

5. **为什么只用一个 worker？是不是只能一个人看？**
   单 worker 仍能处理并发 HTTP 请求。当前采集锁和测速端点锁在进程内，多 worker 会产生多个轮询器和互不共享的锁。要扩展，应先把任务调度与锁协调独立出来，不能直接把 worker 数量加大就宣称扩容成功。

6. **为什么选择 SQLite？能不能同时读写？**
   当前环境便于以单个数据库部署、备份和复现实验。代码启用了 WAL、事务和 5 秒忙等待。WAL 允许读写并行，但同一时刻仍只有一个写入者；没有做大规模压测，不能据此宣称任意规模都适用。参见 [SQLite WAL 官方说明](https://www.sqlite.org/wal.html)。

7. **HTTP 没有 HTTPS，安全吗？**
   当前服务只监听回环地址，跨机器访问通过 SSH 加密通道；这不是公开互联网 HTTPS 网站。内网 SNMPv2c 读取本身也不能被描述为加密安全。若未来公开部署，还需单独设计 TLS、用户认证和网络边界。

8. **网页没有令牌输入，为什么能管理？**
   网关从当前 Windows 用户的加密存储读取令牌，在受限上游请求中附加 `X-Admin-Token`。浏览器发的是本机授权标记，未拿到真实令牌。网关检查 Host、Origin、浏览器来源信息、允许写入路径和请求体大小；这不能防御已经控制当前 Windows 用户的恶意程序。

9. **新电脑为什么不能直接复制原来的加密凭据？**
   DPAPI 密文与 Windows 用户/环境绑定，不能把复制文件当作正常迁移办法。新电脑需要自己的接入条件和授权初始化；这与 DEV 服务账户到测试主机的测速 SSH 授权是两套不同关系。

10. **读取和写入是不是都需要同一个令牌？有没有账号权限管理？**
    普通业务 GET 主要用于读取，管理 POST 要求令牌；`/auth/status` 虽是 GET，也用于验证管理授权。当前没有多用户账号体系和细粒度角色权限，不能说已经实现 RBAC。

11. **服务重启后数据会丢吗？如何回退？**
    已提交数据保存在 SQLite，不依赖浏览器内存。部署工具提供摘要/归档校验、备份及失败回退逻辑。本次只是三个静态 JS 文件的备份与原子替换，没有重启 DEV 服务或迁移业务库；不能把这次操作说成完成了所有真实回退演练。

#### 采集参数与 OID 速查

| 内容 | 当前实现口径 |
|---|---|
| 目标 | 周期采集筛选 4 个 `router-candidate` 和 3 个 `test-host`；不扫描整个地址段 |
| SNMP 传输 | 对目标 IPv4 的 UDP/161 发送 SNMPv2c 读取请求 |
| 表读取 | 优先 GETBULK，每批最多 8 项；失败时尝试 GETNEXT；限制 OID 前缀、递增方向和行数 |
| 源码默认限制 | SNMP 单次等待 1.5 秒；接口 16、路由 64、地址 64；这些是默认配置，不是声称所有部署环境永远固定 |
| 故障阈值 | 默认 3，由 `NMS_FAULT_THRESHOLD` 配置 |
| 后台间隔 | 已核实 DEV `poll_interval_s=15`，表示轮次结束后等待 15 秒 |

#### 可能追问与回答

1. **GET、GETNEXT、GETBULK 有什么区别？你们用了哪个？**
   GET 取已知对象实例；GETNEXT 沿 OID 顺序取下一项；GETBULK 批量取得后续项。项目读取具体字段用 GET，遍历表优先 GETBULK，必要时退回 GETNEXT；它们都是读取，和 SET 写入不同。协议定义见 [RFC 3416](https://www.rfc-editor.org/rfc/rfc3416)。

2. **老师只说开放 GET，你们怎么敢用 GETBULK？**
   不能仅凭课程文字假设所有遍历方式可用。项目在真实目标验证后使用，并保留退回 GETNEXT 及失败/部分结果处理。某个设备不支持时，应记录限制，不虚构完整数据。

3. **15 秒为什么不是实际采样周期？给一个真实例子。**
   汇报核对记录中 run 49611 于北京时间 01:07:58 开始、01:08:34 结束，耗时 36 秒；下一轮 01:08:49 开始。相邻开始时间相差 51 秒，即本轮 36 秒加等待 15 秒。其他轮次可能更长或更短，不能把此例当固定周期。

4. **一次采集成功，为什么有的速率还是无效？**
   采集成功说明本轮目标读取满足相应条件；速率还依赖上一样本、实际间隔、来源和计数连续性。首样本、超过 60 秒的间隔等都会使派生指标无效，两种状态不矛盾。

5. **为什么有时一轮耗时很长？能直接并发采集吗？**
   当前按目标和字段顺序读取，网络等待与多个 SNMP 请求累积成轮次耗时。并发是可研究的优化，但需要控制目标负载、事务、采样时间和失败隔离；当前没有把并发采集作为已完成能力。

6. **一个设备失败会不会把全部采集终止？**
   已对目标级常见错误隔离，轮次可标为 `partial` 并保存每个目标的结果。没有记录或查询失败不等于目标没有接口、地址或路由。

7. **如何防止响应串包或错误表项？**
   SNMP 客户端校验来源地址/端口、版本、community、request-id，GET 还核对请求 OID；遍历拒绝不递增 OID。它是本项目所需的有界实现，不应夸大为覆盖全部 SNMP 标准与所有设备兼容性的通用库。

8. **为什么保留原始样本，不只存图表数字？**
   速率、流量和告警都需要回查依据。计数样本、指标样本、事件关联编号、来源和时间共同支持排查；保存这些会增加数据量，后续需要保留与归档策略。

9. **刷新页面会不会增加设备负载？手动采集会不会和后台重叠？**
   普通刷新只查询数据库，不发 SNMP；手动采集才会触发轮次。采集锁会拒绝同时发起的另一个轮次，不会无限排队或偷偷重叠。

10. **所有接口的测量时间是同时的吗？时钟是否做了同步校准？**
    不是同步测量。当前每个路由候选进入采集时记录时间，再顺序读取接口字段，因此时间粒度和轮询偏差有局限；跨主机高精度时钟校准未作为本次已验证能力。分析应结合采样窗口，不能把所有字段视为同一瞬间的抓包结果。

#### 故障规则的精确口径

| 情形 | 当前程序如何处理 |
|---|---|
| 每次 ping | 从 DEV 发起 `ping -n -c 2 -W 1 -w 3 <地址>`；最后的 3 秒是默认总截止配置 |
| 本轮两个探测包都未收到响应，且输出可解析 | 记为 `query_status=ok, loss_pct=100`，累计不可达次数 |
| 命令不可用、超时终止或输出不可解析 | 记为测量未知/失败，不把它当成已确认的 100% 丢包 |
| 连通性告警 | 默认累计达到 3 次有效观测中的完整丢包；有效非 100% 丢包会清零 |
| 接口告警 | 有效读取且 `admin=up, oper=down`，默认累计达到 3 次 |
| 未知观测插入中间 | 当前实现保留既有计数，不增加、也不重置；因此严格说是“有效观测序列中的连续异常” |
| 告警持续 | 更新原事件及证据，不每轮新增一条同类活跃事件 |
| 确认 | 记录已知悉时间，故障状态可以仍为 `active` |
| 恢复 | 后续有效观测不再满足该异常条件，事件变为 `recovered` |

当前四条告警分别对应 `r-0-1:12`、`r-0-2:12`、`r-0-5:12`、`r-0-8:12`，描述都是 `virbr0`。它们不能证明四台设备宕机或业务链路中断。

#### 可能追问与回答

1. **为什么要三次，不一次就告警？**
   是降低偶发丢包或瞬时状态变化影响的工程阈值，可配置，未宣称通过统计建模证明“三次最优”。代价是检测更慢；阈值越高，通常越不敏感。

2. **三次异常等于 6 个 ICMP 包连续丢失吗？**
   在默认每轮 2 包且三次观测都有效时，共涉及三轮中的 6 个探测包，但轮次之间存在等待，不能说是连续不断发送的 6 包。测量未知还可能保留计数，因此不能把它解释为严格无间隔的 6 包序列。

3. **多久能发现故障？是不是 45 秒？**
   不能按 `3×15` 算。若相邻同目标观测约 51 秒，第一次失败到第三次失败约需两个间隔，另有故障发生相位和采集耗时；中间未知会进一步延长。当前没有承诺固定检测 SLA，应报告实际时间戳。

4. **未知为什么不重置？长时间没采到后还累计合理吗？**
   当前策略是“没有有效证据就不改变既有判断”，避免把读取失败当恢复。局限是未知间隔过长后旧计数仍可能沿用；可在后续引入观测有效期或时间窗阈值，当前未实现这一增强。

5. **50% 丢包算恢复吗？把接口管理状态改为 down 算恢复吗？**
   对“完全不可达”这条规则，任一次有效的非 100% 丢包会清除该异常条件，50% 丢包也如此；并不代表服务质量恢复正常。接口管理状态不再为 up 时，`admin=up且oper=down` 条件也解除；这不是证明线缆或业务已经修好。

6. **virbr0 是什么？为什么不直接过滤掉？**
   该名称表示观测到的虚拟网桥接口，但我们尚未独立确认它在课程环境中的用途。保留接口状态并标注业务影响待确认，比无依据删除告警更诚实；后续可按已核实的业务角色制定排除或分级规则。

7. **ping 不通可以证明设备坏了吗？**
   不能，也可能是 ICMP 策略、路径或测量端问题。当前诊断会给出这些可能原因，而不会直接写成“硬件故障”。同理，ping 通不代表 HTTP、SSH 或其他应用业务正常。

8. **诊断怎样关联接口，为什么不能直接确认根因？**
   需要主机 100% 丢包、同来源的最近完整地址发现、接口管理 up/运行 down、地址和接口状态与 ping 的时间差均不超过 60 秒，且目标地址属于该接口观测子网。它证明时空关联，不能证明因果；接口采样超过 5 分钟等情况还会标为历史。

9. **告警 first_seen 是故障真正开始的时间吗？证据列表包含触发前全部样本吗？**
   不保证。当前事件在达到阈值时创建，`first_seen` 是该时刻；初始关联证据是触发样本，后续持续/恢复样本追加进事件。触发之前的样本应去历史表查，不能说事件自己保存了故障开始前的完整现场。

10. **怎样证明恢复逻辑有效，为什么还说缺真实案例？**
    本地构造测试验证状态流转、去重和确认逻辑；真实页面已能显示实际告警。尚缺经批准的真实故障出现、触发、恢复及各阶段证据完整对应的案例，两个层级要分开。

11. **重复确认会改变故障时间或再次触发采集吗？**
    不会重新探测设备。确认操作只在首次确认时保存确认时间；已有确认记录不会通过重复点击变成新的恢复证据。

#### 可能追问与回答

1. **IP 和掩码怎么变成子网？**
   使用 IPv4 地址与掩码计算网络前缀。例如 `192.168.1.9 + 255.255.255.252` 得到 `192.168.1.8/30`。地址表还给出接口索引，因此能把地址关联到 `r-0-1:4 / ens5`。

2. **实线就是真实直连吗，图中的 confirmed=true 是什么意思？**
   实线确认的是“地址表观测到接口属于这个子网”。代码另有 `physical_link_confirmed=false`，并未确认物理直连。两台设备接在同一交换网络、虚拟桥或不同隔离环境，都不能只靠同前缀确定布线。

3. **为什么课程画 /24，实测却有 /30 和 /29？是不是老师图错了？**
   课程示意和实际接口前缀是不同层次的证据。我们分别呈现，不自行把任意一方改写成另一方；如果需要解释具体实验拓扑，应结合课程配置确认。

4. **为什么 27 个地址只画 23 条实测关系？所有 lo 都过滤了吗？**
   当前恰好排除了四个 127/8 回环网络地址。过滤依据是网络地址性质等条件，不是接口名 `lo`；所以配置在 lo 上的 `1.1.1.1/8` 等仍可能画出关系。它们也不能据此解释为物理链路。

5. **看到 1.1.1.1 或 8.8.8.8，是测到了公网 DNS 吗？**
   不是。这里是设备地址表返回的本地接口配置，其中这些地址位于 lo 上；没有因此验证互联网或公共 DNS 的连通性，也没有把公网服务作为本次测量目标。

6. **四个 virbr0 都有 192.168.122.1，是不是一定地址冲突？**
   不能直接判断。它们可能处于不同的虚拟或隔离网络。当前图按 IPv4 前缀组织关系，尚未建模 VRF、VLAN、网络命名空间等隔离域；同前缀聚合可能造成视觉上的过度关联，这正是不能把它当物理拓扑的原因。

7. **sysName 相同能合并设备吗？目前看到哪些名称？**
   汇报读取记录分别有 `FRR-R1`、`FRR-R2`、`FRR`、`FRR-R8`。名称是辅助线索，不保证唯一性，也不能作为完整物理身份凭证；当前不自动合并。

8. **地址表读取失败后，为什么有些关系会消失？是不是网络真的断了？**
   拓扑只使用每个设备最近一次完整成功的当前发现条件；若最近一次尝试失败，不偷偷回退旧成功数据冒充新观测。消失说明缺少本次可用依据，不等于已经证实配置删除或链路中断。接口和路由又有各自保留历史的语义，需看时间。

9. **快照每轮都新增吗？比较什么？**
   内容与上一份一致时复用已有快照，不每轮复制。比较同一设备的接口描述/状态/参考速率、路由和地址映射，列出新增、删除、变化；任一侧未完整提供的章节跳过，不能误判为删除。

10. **为什么前后有两个快照，却还说没有真实配置变化案例？**
    快照可能因功能升级新增字段而产生，例如旧快照没有地址章节。当前页面比较曾显示接口/路由无变化、地址章节未比较；这不能拿来证明实验网络真的发生过配置变更。

11. **怎样才能进一步确定实际链路和设备身份？**
    可考虑经允许读取 LLDP/CDP、桥转发表、邻居/ARP 表，结合接口 MAC、设备标识、VRF/VLAN 和课程侧配置交叉核实。当前没有证明这些接口全部开放，也没有实现完整物理拓扑发现，应把它们作为条件性方案。

#### 性能指标的公式与有效性

| 指标 | 计算与单位 |
|---|---|
| RTT | DEV 发出 ICMP 到收到回应的往返时延；代码对解析到的回应耗时取平均，单位 ms；不是单向时延 |
| 丢包率 | `(发送包数－接收包数) / 发送包数 × 100%`；默认每次 2 包，结果较粗 |
| 入方向速率 | `8 × (当前入字节－前次入字节) / 两次记录的实际秒数`，单位 bit/s |
| 出方向速率 | 同样对出方向累计字节差分，单位 bit/s |
| 利用率 | `方向速率 / 正的参考速率 × 100%`；参考速率未知则为空 |
| 参考速率 | 优先 `ifHighSpeed × 1,000,000`；没有可靠正值时尝试 `ifSpeed` |
| 趋势窗口 | 当前查询最近最多 120 条样本，按实际时间显示；不是固定的 120 秒 |

**解释用示例，不是实测记录**：计数器在 10 秒内增加 1,000,000 byte，速率为 `8×1,000,000÷10=800,000 bit/s=0.8 Mbit/s`。若参考速率为 100 Mbit/s，则这一方向利用率为 0.8%。

无效原因包括：读取失败、首样本/前样本无效、来源变化、时间不递增、间隔 **超过 60 秒**、sysUpTime 下降、计数不连续标记变化、累计计数下降。无效区间保留原因，不画成正常的零值，也不用于正常流量求和。

#### 可能追问与回答

1. **为什么使用 64 位，不用 32 位？**
   高速接口的累计计数可能快速超过 32 位范围，64 位提供更大的计数空间。项目读取 `ifHCInOctets/ifHCOutOctets`；遇到不支持的设备不会擅自把缺失值补零。计数对象定义见 [RFC 2863](https://www.rfc-editor.org/rfc/rfc2863)。

2. **计数回绕或设备重启后如何处理？**
   当前保守地把累计值下降、sysUpTime 下降或不连续标记变化的区间标为无效，不推算一次回绕后的流量。sysUpTime 下降是判断依据之一，不能单独当作硬件故障证据。

3. **为什么字节数在 JSON 中是字符串？**
   uint64 上限为 `2^64−1`，而 JavaScript Number 只能精确表示到 `2^53−1` 的整数；SQLite 普通整数也不能容纳全部无符号 64 位范围。累计字节和汇总量用十进制字符串保存/传输，后端 Python 整数运算保持精确；速率则是派生浮点数。

4. **bit/s、byte 和 Mbit/s 怎么换算？**
   1 byte 为 8 bit；本项目 Mbit/s 使用十进制 `1,000,000 bit/s`。不能把 10 Mbit/s 说成 10 MB/s，后者大 8 倍。

5. **当前丢包率 0%，能证明网络没有问题吗？**
   只能说明该次有限探测包收到回应。每次仅两包，短时结果不能代表长期丢包概率、所有应用服务或所有路径；要更强结论，需要更长时段和明确的测量方案。

6. **为什么 RTT 很小？为什么有尖峰？**
   这里测量的是 DEV 到内网目标的往返，不包含维护电脑的 WARP/SSH 接入时延。尖峰可能受调度、排队等影响，但当前没有细分原因的证据，不应直接归因于攻击或某台设备性能不足。

7. **为什么利用率空白，明明有速率？**
   字节差能计算流量速率，但利用率还需要可靠参考容量。虚拟接口可能不报告有效参考速率；留空比随便用 1 Gbit/s 做分母更合理。

8. **超过 60 秒就无效是否过于严格？采集不是经常几十秒吗？**
   这是当前固定的有效间隔上限，并不由 15 秒配置自动换算。轮次变慢时确实可能产生无效区间和报表缺口。应评估采集耗时与该阈值是否匹配，不能为了让图好看而事后掩盖缺口。

9. **为什么图上的速率和 iperf3 结果不同？**
   接口速率是某接口在采样区间内的平均值，可能含多种业务；iperf3 是特定端点、特定短时任务的吞吐结果。观测点、窗口和统计层次不同，不能直接要求相等。

10. **入、出利用率可以相加判断满载吗？**
    当前分别计算方向利用率；风险规则检查任一方向达到阈值。不能不考虑接口和双工语义，就把两方向简单相加当作一个容量占比。

11. **不支持高容量计数器、参考速率错误、采样时间有偏差怎么办？**
    当前会对无法读取的计数标明未知，但设备报告值是否准确、顺序采样带来的时序偏差仍是测量限制。系统没有外部校准工具或线速对照实验，不应把指标精度说得超出证据。

#### 可能追问与回答

1. **这是 TCP 还是 UDP？为什么 -b 也能限制 TCP？**
   当前命令没有 `-u`，是 TCP 测试；`-b` 设置目标比特率，可用于 TCP。项目保存的任务参数也写明 `protocol=tcp`。参数定义见 [iperf3 官方说明](https://software.es.net/iperf/invoking.html)。

2. **9.94 Mbit/s 是否证明链路带宽只有 10 Mbit/s？**
   不能。我们主动把目标速率限制为 10 Mbit/s，这次验证的是受控任务流程与结果处理。测最大容量需要另定授权、时长、并发、端点负载与路径条件，目前未做。

3. **2 秒 × 10 Mbit/s 应是 2,500,000 byte，为什么不完全一致？**
   两秒是配置目标时长，实际传输有启动/结束边界和调度影响。程序直接保存 iperf3 报告的接收字节与实际报告速率，不用配置时长强行反推结果。

4. **发送字节多于接收字节，是不是丢包了？**
   不能只用这两个汇总数字的差值判断 TCP 丢包率。两端结束时刻、缓冲和统计边界可能不同；本项目没有把差值当作丢包指标。应结合工具报告、重传及更完整的两端证据分析。

5. **既然三台主机都能 SSH，为什么第三台不能网页测速？**
   人工登录权限与 DEV 的 `nms-team2` 服务账户非交互权限不同。当前仅给 host-1/host-2 配置了专用受限授权和固定主机密钥；host-3 被配置白名单排除，不能绕过前置条件。

6. **为什么不用 root 执行测速？服务端需要 root 吗？**
   任务通过课程提供的 `test-user` 执行，在高位端口启动普通进程；DEV 后端也以专用服务用户运行。课程入口的 root SSH 用于部署维护，不等于测速任务需要 root。

7. **怎么避免服务端没起来就启动客户端？**
   服务端包装脚本检查进程存活和 `/proc/net/tcp` 或 `tcp6` 的监听状态，输出就绪标记；管理端等待标记后才启动客户端，失败或超时则记录失败。

8. **重复点击、端点相同、同时测试会怎样？**
   API 拒绝客户端与服务端相同，限制只能选已登记且获准的主机。任务管理器保留活跃端点集合，冲突的任务不会同时占用相同端点；没有实现跨进程分布式调度。

9. **测试会留下监听端口或孤儿进程吗？**
   实现了单次服务端 `-1`、服务端 15 秒保护超时、shell 退出清理，以及客户端/SSH 子进程终止与超时处理。历史现场曾验证测试端口清理；本次只读复查没有重新发起任务，因此不能说本次又做了一次完整现场清理测试。

10. **随机端口一定不会冲突吗？**
    不能保证外部进程没有占用。当前随机选择后依赖服务端启动与就绪检查来识别失败；未实现对全系统端口的排他预留，也不会为消除冲突随意杀掉别人的进程。

11. **页面里为什么还留着失败任务？这算功能没做好吗？**
    历史上有服务端 SSH 未就绪的失败任务，保留它用于排障。后来成功任务证明流程已打通，但不应删除失败历史来制造“从未出错”的印象。

12. **测速会影响现有业务吗？**
    任何主动流量都可能有影响，限时限速和白名单降低范围。当前没有充分测量并证明“完全无影响”，不能这样承诺；扩大测试应另行确认实验条件。

#### 可能追问与回答

1. **接口字节和网元对字节为什么不相等？可以加起来吗？**
   不可以。接口计数涉及经过该观测点的流量，iperf3 统计是一次指定端点测试的接收量；业务集合、测量层次和时段边界不同。接口总量也可能已经包含测试流量，相加会产生重复统计。

2. **知道接口属于哪个子网，不就知道哪个主机产生流量了吗？**
   不知道。子网映射只有网络前缀，没有每条业务流的源/目的主机、端口和字节归属。一台接口可能承载多个主机及转发流量，不能把整段总量分配给单一主机对。

3. **你们到底有没有实现“网元间流量统计”？**
   已实现接口方向统计，以及成功受控任务的明确网元对统计；尚未覆盖普通业务的全部任意网元对。应说明这两个范围，再请老师确认是否满足当前课程粒度，不回答笼统的“完全实现”或“完全没做”。

4. **为什么最近 15 分钟常常不是 100% 覆盖率？**
   用户选择的时间边界通常不与采样端点对齐，另外可能有查询失败或超过 60 秒的无效间隔。当前不插值补齐。100% 是特定历史窗口的结果，不应说任意窗口都达到 100%。

5. **没有有效区间时结果是不是 0？**
   不是。当前返回未知值而不是伪造零流量；只有存在有效区间、字节增量确实为零时，零才是有依据的观测结果。

6. **完整窗口 complete=true 有什么条件？**
   要有纳入区间，第一段起点和最后一段终点与窗口相符，覆盖总长度匹配窗口，且没有无效区间。不能只因为显示四舍五入后的覆盖率为 100%，就断言所有完整性条件都成立。

7. **为什么不对边界区间按比例估算？**
   那需要假设区间内流量均匀，而短时测试或突发流量可能不满足。当前选择可解释的保守统计；如果未来增加估计值，应单独标明模型和误差，不与直接观测总量混用。

8. **测试跨过窗口、失败或取消，怎么计费？**
   当前网元对汇总只纳入状态成功、接收字节有效、完整落在窗口内的 iperf3 任务；跨边界任务排除，不按时间比例分摊。失败/取消不算成功测试量，因此也不能把结果叫“所有实际发生过的传输量”。

9. **统计期间接口 IP 变了，会不会把流量算错子网？**
   会检查窗口起点前最近地址映射的有效性，超过 5 分钟则标旧；检查窗口内发现是否完整且映射一致。读取失败或地址变化时，不把整段流量归给单一子网。未采样期间发生又恢复的变化仍可能无法发现。

10. **CSV 和页面是两个独立统计程序吗？时区怎么处理？**
    CSV 使用相同统计范围与参数；本次已对照历史网元对数字。页面输入/显示固定北京时间，后端窗口统一转 UTC；例如 21:55:38 对应 `13:55:38Z`，不是把本地时间直接当 UTC。

11. **为什么不能把所有接口入、出相加得到全网流量？**
    同一传输经过多跳会在多个接口被记录，两个方向和多个候选还可能产生重复观测。全网总量需要先定义观测边界和去重策略，当前没有提供这个结论。

12. **进一步做全业务网元对统计，需要什么？**
    可评估 NetFlow/IPFIX、已有流日志或经允许的等价观测，至少需要端点、方向、字节、时间与观测位置；还需处理采样、NAT、重复导出和丢失。能否拿到这些数据是前提，不是画个饼图或读取 ARP 表就能补齐。

#### 安全规则实际检查什么

| 规则 | 触发依据 | 不能推出的结论 |

| 意外开放端口 | 已登记基线“不允许开放”，TCP 连接成功 | 不能识别实际应用协议或软件版本 |

| 持续高利用率 | 最近 3 条指标均为有效 live 样本，每条至少一个方向利用率达到 80% | 不能证明 DDoS，不能定位攻击者 |

#### 可能追问与回答

1. **默认团体字到底验证到了哪一层？**
   证据是从 DEV 管理端成功执行 SNMPv2c 只读查询，且命中代码内两个常见默认值。没有从其他网络测试暴露面；记录明确标注未确认漏洞、未识别攻击源。风险证据不保存实际团体字明文。

2. **换一个非默认团体字成功读取，旧风险会自动消失吗？**
   不会。新凭据可用不能证明旧凭据已撤销。当前实现保留旧风险，需要维护方核实默认凭据和访问控制策略，并补充独立修复证据。

3. **端口连接失败就表示安全了吗？**
   不成立。明确拒绝连接记为 `closed`；超时和其他网络异常记为 `unavailable`，表示没有确认状态。开放端口也不一定危险，要结合用途、权限和服务基线。

4. **保存服务基线会关闭远端端口吗？**
   不会，只保存“该设备该端口是否允许开放”的管理预期。主动检查还要求 live 模式、功能开关开启、管理授权、登记目标和已有基线；不是任意地址的全端口扫描器。

5. **应该开放的服务关闭时，会产生故障吗？**
   当前这一安全规则只检测“不允许却开放”，没有实现“允许开放但关闭”的服务可用性告警，不能把基线功能说成双向完整监控。

6. **基线允许 TCP/23，就不会提醒 Telnet 吗？**
   不是。意外开放端口与潜在 Telnet 是两条独立规则。TCP/23 开放仍可产生协议待核实的线索，基线允许不等于已确认安全。

7. **高利用率必须同一方向连续三次超过阈值吗？**
   当前不要求方向相同。最近 3 条指标中，每条入或出至少一项达到 80% 即满足；它们都必须是有效真实样本。无法取得参考容量就不能凭空算利用率，不能按零利用率处理。

8. **高利用率风险怎样恢复？**
   当前有效样本低于阈值会解除；无效样本或缺少利用率不会作为恢复依据。正常备份、测速也可能造成高利用率，应先解释流量背景，不能直接归因攻击。

9. **确认、解除和修复是什么关系？**
   确认表示有人看过，解除表示对应规则不再满足。意外开放端口风险在观测到关闭，或后续检查时基线已改为允许，均可能解除；后者是策略变化，不代表物理端口被关闭。仍需说明解除原因。

10. **为什么没定位攻击 IP 或验证具体漏洞？**
    当前接口计数和 TCP 连接结果缺少足够的会话、协议和漏洞证据。攻击源判断需要获准的流记录或相关日志；漏洞确认需要范围明确的验证方案。这两项仍是验收深度待确认的缺口。

11. **发现默认 SNMP 风险后为什么不直接修？**
    课程设备配置由维护方管理，当前接口读取权限不等于修改权限，也没有把 SNMP SET 修复实现成能力。应先核实凭据与 ACL 的预期，再由获准操作补齐修复前后证据。

12. **网页管理授权和安全管理模块是一回事吗？**
    不是。网页授权保护本系统的管理写操作；安全模块记录实验网络的风险线索。前者可用不能证明实验网络安全，后者有告警也不等于本系统账号失守。

| 多窗口查询并发 | 查询编号递增；开始时清空旧表；返回时核对编号 | 旧查询可能仍在服务器执行，仅禁止覆盖当前界面 |
| CSV 与界面错位 | 查询完成前隐藏旧导出；过期响应不覆盖当前数据 | 只保证当前查询状态一致，不扩展底层观测范围 |
| 换机启动 | 本机凭据、WARP/IPv6 接入、SSH 隧道、网关逐项检查 | 接入层仍可能断连，不能承诺永不掉线 |

#### 可能追问与回答

1. **为什么读请求 30 秒，写请求 75 秒？**
   手动采集的 POST 要等待完整轮次，已观察到一轮超过 30 秒；本机网关上游等待为 70 秒，所以前端为写操作保留 75 秒。不是所有业务正常情况下都要等这么久。

2. **超时后为什么不自动重试写操作？**
   服务端可能已受理，只是响应没回来。自动重发可能重复触发操作。页面提示先恢复连接、查看采集或任务记录，再判断是否重试；AbortController 结束客户端等待，不提供服务端回滚保证。

3. **只限制 fetch 为什么不够？**
   收到响应头后，JSON 正文仍可能停滞。公共请求封装把等待覆盖到 `response.json()` 完成，最后清理定时器和外部取消监听。

4. **旧查询怎么覆盖新查询？现在怎么挡住？**
   例如先查 15 分钟窗口 A，再查 1 小时窗口 B；B 先返回，A 后返回。现在 A 的请求编号已经过期，不能再改当前表格、状态和 CSV。成功和失败分支都要核对编号，避免旧错误覆盖新结果。

5. **请求编号是不是数据库事务？**
   不是，它解决页面异步响应的先后问题；不改变数据库事务，也不取消服务器已开始的工作。一个窗口的不同统计仍需遵守各自数据来源和范围。

6. **修复怎么验证过？**
   本次网页修复阶段已有 Python 109 项及 4 组前端回归通过的记录；前端专门检查响应头/正文停滞、读写期限、不自动重试和过期查询。真实浏览器还核对历史查询、CSV、模拟超时后恢复刷新。文档改版没有重新宣称进行一次完整业务验收。

7. **浏览器检查是否真的等了 30 秒，是否测了所有写功能？**
   超时场景包含缩短等待的受控模拟，用来验证状态恢复；代码测试另核对生产期限。最终浏览器复核使用只读 GET，没有新发真实测速、端口探测或告警确认，因此不能把它说成所有现场写操作都验证过。

8. **为什么新电脑会找不到 admin-token.dpapi？**
   这是本机当前 Windows 用户的加密凭据文件，新机器尚未初始化时不会自动存在。它不应进入仓库，也不能把旧用户加密文件当成通用授权材料。需要正确初始化本机授权，并分别检查网络接入和隧道。

9. **WARP 断开是不是 DEV 服务坏了？**
   不一定。访问经过本机网关、SSH 隧道和接入网络；其中一层断开就可能打不开页面。先按启动器步骤定位；授权失败与上游不可达也要分别检查，不能看到页面失败就重装后端。

10. **修复是否已经更新到运行环境？**
    网页的三个 JS 文件已备份后更新 DEV，最终 HTTP 文件摘要与本地源码一致；本次静态更新未重启服务或改业务数据库。这里的部署成功不等于本地所有变更都已提交或推送 GitHub。

11. **本地网关能防所有攻击吗？**
    不能。它把 DEV 管理令牌留在本机进程，校验本地请求并代加授权，降低令牌进入页面的需要；不能保护已被恶意程序控制的本机账号。SNMPv2c、网络访问控制和设备凭据还要分别评估。

1. **距离老师要求最核心的差距是什么？**

2. **把计费页面补漂亮一点就能解决吗？**
   不能。缺的是观测数据，接口总量没有端点对明细。先确认要求，再评估设备是否能提供所需数据及获取权限，最后才是统计与展示。

3. **为什么不能把四个路由候选直接当成四台物理路由器？**
   地址、sysName、接口表只能提供身份线索；虚拟环境和多地址访问可能影响映射。当前按候选保留数据，需要课程侧身份信息或更强证据，不能未经核实合并或断言数量。

4. **不是有测试了吗，为什么还缺恢复案例？**
   测试能验证输入与状态机行为；真实恢复案例还要有现场初始状态、获准操作、恢复观测和关联证据。样例数据、功能升级引起的快照变化都不能替代这一过程。

5. **能现在断一条链路做演示吗？**
   先确认实验权限、影响范围和恢复方式，再安排受控场景。当前材料没有把随意断链或修改课程设备当成已获准操作。也可以先用明确标注的隔离样例解释状态机，但它仍不是现场证据。

6. **238 万条是什么意思，是否等于数据库很大或很慢？**
   是本轮 overview 记录的历史指标行数，精确值为 2,381,073；不是设备数、每秒采集量或数据库字节数。还没给出容量和耗时基准，不能仅靠行数宣称慢或推算磁盘占用。

7. **快照已经去重，为什么数据还会增长？**
   配置快照与持续采集的指标、原始计数、地址观测不是同一类数据。快照去重不等于所有历史表都有保留上限；事件证据也需要评估增长方式。

8. **准备如何优化？已经实现了吗？**
   先测常用查询耗时、数据量和实际访问模式，再评估索引、分页、查询范围与归档/保留期。当前把它列为后续工作，没有宣称自动清理、降采样或容量保障已经完成。

9. **删旧数据会不会把验收证据删掉？**
   有这个可能，因此保留策略应区分日常采样与验收案例、原始依据、导出报表，并先验证备份恢复。这里只提出方案，没有执行删库或清理历史。

10. **回归都通过是不是说明没有 bug？**
    只能说明已有检查覆盖的行为通过。长期负载、网络异常组合和现场权限差异仍可能暴露问题；当前也没有完整压测和全面安全审计结论。

   全业务流量与受控测速统计需要不同数据来源，安全线索与漏洞验证也需要不同权限和证据。先锁定验收口径，才能安排有明确产物的工作。

3. **故障模块怎样算补齐现场验收？**
   在获准场景中保留正常状态、连续有效异常观测、触发告警、人工确认和有效恢复观测。特别展示确认不改变故障事实；未知观测也不能被当成恢复。

4. **配置模块需要什么变化案例？**
   两份来源一致、采集完整的现场快照及其差异，说明改了什么、为什么获准、何时恢复。不能拿采集字段增加或页面升级造成的差异冒充设备配置变更。

5. **性能与计费如何验收？**
   至少能解释两次有效计数与时间差、无效区间原因、受控测速参数和原始结果。统计要固定窗口、对象、方向和来源，用页面、API、CSV 核对一致性，同时明确覆盖不足的范围。

6. **安全模块怎样证明风险恢复？**
   对具体规则提供风险依据、获准处理、处理后的独立观测和状态变化。例如改管理端使用的凭据不足以证明旧默认凭据已禁用；基线改成允许也不能说成关闭了端口。

7. **第三台测试主机还要补什么？**
   需要课程允许的专用 SSH 授权、主机身份校验、可执行的测试程序和受限任务流程，再补正常与失败记录。知道 IP、能 ping 通，不等于管理服务账号能无交互执行测速。

8. **最终怎么交给一台新电脑使用？**
   按发布版本验证网络接入、依赖、当前用户授权初始化、SSH 与本机网关，再核对健康状态和页面数据来源。教程不能依赖开发者机器上未说明的私有文件，凭据也不能打包进仓库。

9. **能否直接修改 SNMP 或开启流导出？**
   要先取得相应课程设备操作权限，确认影响和回退方式；现有只读权限并不覆盖这些配置变更。先把需要的数据字段和验收目标说明白，再安排维护方协作。
