# 蒋天乐：总体架构、后端基础与部署集成

第 2 组｜组长｜网络管理系统项目准备及后续实施职责

你的主要任务是搭好四个模块共用的系统基础，协调数据与接口，最终把各成员的成果集成为部署在 DEV 上的网络管理系统。功能方案依据[总体草稿](../开题报告_第2组_10页口播稿.md)，具体分工可在组内讨论后调整。


## (1) 各功能预期完成效果

你负责的预期成果是一个部署在 DEV、能够统一访问五项管理功能的系统平台。设备、告警、性能、流量和风险数据应采用一致的标识与格式，用户能够从网页查看当前状态、历史记录和测试结果。五项业务功能的具体逻辑由对应成员实现，你交付公共基础、集成结果和运行说明。

| 工作 | 你负责交付的内容 |
|---|---|
| 总体架构 | 数据采集、分析、存储、API、网页之间的关系图；模块目录与调用关系 |
| 后端基础 | FastAPI 项目入口、路由挂载、公共配置、统一错误处理和任务状态 |
| 数据库基础 | SQLite 初始化与表结构管理；统一的读写接口；与成员确认模块字段 |
| 调度与集成 | 周期采集和手动测试的执行入口、超时与并发控制；接入各人的采集与分析函数 |
| DEV 部署 | 依赖准备、启动与停止方式、日志位置、网页访问方法、部署说明 |
| 项目组织 | 进度表、每阶段集成检查、老师问题清单、需求与验收记录、最终报告整合 |

各模块负责人编写自己的采集/分析逻辑、接口处理和页面数据接入；你负责公共基础与集成验收。发生数据库字段或 API 格式变化时，由你组织确认并更新约定。

## (2) 各功能预期使用方法与工具

| 方法与工具 | 用在什么地方 | 预期使用方式 |
|---|---|---|
| Python | 公共配置、调度、结果整理 | 各模块按统一输入/输出接入，集中记录任务状态与错误 |
| FastAPI | 后端与 API | 挂载模块接口，为网页提供设备、告警、指标、报表和风险查询 |
| SQLite | 数据持久化 | 保存设备与接口、历史样本、事件、测试任务及结果 |
| HTML/JavaScript/ECharts | 统一网页界面 | 与段景瀚组织公共组件，由各模块负责人接入业务数据 |
| OpenSSH / Paramiko | DEV 内部测试任务与开发访问 | 内部任务在 DEV 直接连接测试主机；本机通过 SSH 访问 DEV 和转发网页端口 |

以上为拟采用的统一工具。开题时说明用途及数据流程，不把尚未实现的平台写成已经完成。

### 实施步骤

1. 与四人确定 Python + FastAPI + SQLite + HTML/JavaScript/ECharts 是否作为统一方案。
2. 约定设备、接口、采样、事件和任务的公共字段，再让成员按该约定准备模块样例。
3. 建立能启动、查询样例数据和显示公共页面的最小项目。
4. 将金海的采集函数、元泽瑞的性能任务、段景瀚的风险检查接入统一调度；每个任务记录来源、时间、状态和错误。
5. 在 DEV 完成一次从真实采样到入库、API 查询、页面显示的完整验证。
6. 收集每个模块的验收记录，整理一套可复现的演示步骤和部署说明。

开题前主要交付方案与接口样例；完整系统属于开题后的实施目标。

### 需要组织确认的公共约定

以下为建议约定，确认后所有模块共用。

| 项目 | 约定内容 |
|---|---|
| 设备标识 | `device_id` 稳定唯一；IP 地址作为设备属性，多个 IP 不自动算成多台设备 |
| 接口标识 | `interface_id` 唯一，关联 `device_id` 与 `if_index`；接口索引只在对应设备内解释 |
| 时间 | 保存明确时区的采样时间 `sampled_at`；建议统一存 UTC，界面显示北京时间 |
| 单位 | 字节量用 byte、速率用 bit/s、RTT 用 ms、丢包率用 0～100 的百分数；前端换算后标明单位 |
| 缺失数据 | 不可读、超时、首次采样无法差分等情况保留原因，不填造假的零值 |
| 数据来源 | 区分实时采集与测试/回放数据，保留来源说明 |
| 任务状态 | `pending`、`running`、`succeeded`、`failed`、`cancelled`；结果与错误分别保存 |
| 配置与凭据 | 接入配置集中管理；共享职责文件、API 返回和汇报材料不包含密码或 community |

模块首次交付时应包含：一份输入/输出样例、调用方法、错误样例、依赖说明和验证记录。API 路径、表名与字段在首次联调前由你组织确定，避免各人自行建立不兼容的数据结构。

### 实施所需的模块输入

| 成员 | 对方交给你 | 你交给对方 |
|---|---|---|
| 金海 | 设备/接口/路由数据、可复用的 SNMP 与 ping 采集函数、故障事件 | 存储与调度入口、公共标识规则、配置和告警接口挂载方式 |
| 元泽瑞 | 指标样本、iperf3 任务结果、流量汇总及导出逻辑 | 历史数据查询基础、手动任务执行入口、并发和超时机制 |
| 段景瀚 | 安全风险结果、公共页面组件、前端需要的字段清单 | 风险存储与接口基础、各模块接口样例、部署后的访问入口 |

金海负责 SNMP 公共访问逻辑；元泽瑞在同一访问逻辑上提出计数器采集需求。金海的 ping 样本可供元泽瑞复用。段景瀚组织公共界面，各模块负责人共同完成各自页面的数据接入。

### 部署与验收标准

- [ ] 系统能够按部署说明在 DEV 启动和停止，网页可以访问。
- [ ] 至少一条真实数据完成“采集—解析—入库—API—页面”的流程。
- [ ] 五项功能使用一致的设备/接口标识、时间和单位。
- [ ] 一个模块查询失败时，其他模块仍能工作，并能查到错误原因。
- [ ] 重启后历史记录保留，采集任务按预期恢复，手动任务有明确状态。
- [ ] 同一实验端点的 iperf3 测试不会由多个成员同时无序发起。
- [ ] 五项基础功能都有操作步骤、结果记录和已知限制。

系统应运行在 DEV。当前本机已验证 WARP 本地代理配合 SSH 可以连接 DEV；这属于开发接入条件，不应成为服务器内部采集的依赖。网页访问可使用 SSH 端口转发，具体步骤写进部署说明。
