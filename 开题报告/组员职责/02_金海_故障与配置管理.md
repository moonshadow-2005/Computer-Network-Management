# 金海：故障管理与配置管理

第 2 组｜网络管理系统项目准备及后续实施职责

你的主要任务是建立可解释的设备、接口与路由信息，发现连通性和接口状态异常，提供故障告警及恢复记录。这些设备信息和采集能力也为性能、计费和安全模块提供基础。方案依据[总体草稿](../开题报告_第2组_10页口播稿.md)。

## (1) 各功能预期完成效果

**故障管理：** 用户能够查看设备可达性与接口状态，看到持续异常的告警、证据、首次发现时间，以及恢复后的记录。

**配置管理：** 用户能够查看设备/接口清单、路由与可解释的逻辑拓扑，对比两次配置快照的新增、缺失和变化。

| 工作 | 你负责交付的内容 |
|---|---|
| SNMP 公共访问 | 可复用的只读查询函数、超时/错误处理、可读 OID 与索引验证记录 |
| 设备与接口发现 | 设备地址、接口索引/描述/状态，能够读取时的地址及设备信息 |
| 路由与逻辑拓扑 | 路由目的、掩码、下一跳、出接口关联；带数据依据的拓扑节点和连接关系 |
| 配置快照 | 保存可读配置，比较新增、缺失和变化，提供变化记录 |
| 连通性采集 | ping 可达性、RTT、丢包样本，供本模块与元泽瑞复用 |
| 故障判断 | 连续异常确认、告警去重、恢复记录与诊断线索 |
| 模块展示与材料 | 设备/拓扑与故障页面的数据接入、操作说明、验证记录 |

配置管理在本项目中首先实现探测、记录与变化对比。附件未开启 SNMP SET/TRAP，采集与告警采用周期查询，不能依赖自动修改配置或设备推送通知。

## (2) 各功能预期使用方法与工具

| 功能 | 方法与工具 | 数据与使用方式 |
|---|---|---|
| 故障管理 | Python 调度 ping、SNMP 只读查询 | 获取可达性、RTT/丢包与接口状态；连续异常确认、去重、恢复记录 |
| 配置管理 | Net-SNMP 的 `snmpget`，条件允许时使用 `snmpwalk` | 查询接口与路由信息，保存快照并比较变化；表遍历能力单独验证 |
| 拓扑展示 | 设备/接口/路由关联分析，公共网页组件 | 根据采集证据和课程初始拓扑建立逻辑连接关系，标明待确认部分 |

### 先做哪些检查

1. 阅读[课程说明](../../project/docs/课程设计要求.md)并核对原 PDF，把已知地址整理成初始设备候选清单。
2. 获取 SNMP community，先验证明确 OID 的 GET，再验证接口和路由表遍历。
3. 记录哪些 OID、设备和接口索引可读，以及每种失败的实际表现。
4. 建立设备、接口、网段与下一跳之间的关联；保留无法确认的关系与原因。
5. 输出统一 ping 样本和故障状态转换记录。
6. 将结果接入蒋天乐的存储/API，并与段景瀚的公共页面组件对接。

2026-10-02 已在四个连接地址完成只读 GET，并小范围验证 GETNEXT、GETBULK，接口与路由首项可读；完整表遍历、正式凭据及设备身份仍待确认。`snmpwalk` 使用 GETNEXT，见 [Net-SNMP 说明](https://www.net-snmp.org/docs/man/snmpwalk.html)。小范围成功不等于所有表均可完整遍历。

### 配置管理的使用流程与数据

设备页面应能回答：管理对象有哪些地址、接口叫什么、接口处于什么状态、哪些网段直连或经下一跳可达，以及与上次采集相比发生了什么变化。

初期重点读取 `ifIndex`、`ifDescr`、`ifAdminStatus`、`ifOperStatus` 和附件列出的路由表。地址表、设备名称等附加 OID 的可读性需要实测。

拓扑输出至少包含节点、连接关系、关系来源与最后确认时间。文档中子网 1 有 `192.168.0.1` 与 `192.168.0.2` 两个接入关系，应保留；多个地址不能直接认定为多台物理设备。未确认的关系在界面标注为待确认。

### 故障管理的判断流程

| 输入情况 | 需要给出的结果 |
|---|---|
| ping 与 SNMP 均正常 | 当前采集正常，并记录采样时间 |
| ping 失败但 SNMP 正常 | 给出连通性或 ICMP 响应异常线索，保留 SNMP 正常证据 |
| SNMP 超时或无权限 | 查询失败/状态未知及原因，避免直接判为设备宕机 |
| `ifAdminStatus` 与 `ifOperStatus` 不符合预期 | 接口异常记录，包含接口、状态与采样证据 |
| 连续多次异常 | 产生或更新同一持续事件，避免每次采样重复创建告警 |
| 异常后恢复 | 关闭事件并保存恢复时间与持续时长 |

初始建议采用 5～10 秒采样、连续 3 次失败确认，参数与蒋天乐共同配置，并依据实测调整。诊断结果应说明证据；证据不足时显示待确认原因。

## (3) 组员分工与时间计划

全组分工为：蒋天乐负责总体架构、后端/数据库基础及部署集成；你负责故障与配置管理、公共 SNMP/ping 采集；元泽瑞负责性能与计费；段景瀚负责安全与公共界面。你还负责自己两个模块的接口处理、页面数据接入和验证记录。

### 数据交付与协作边界

| 对接人 | 你提供 | 你需要 |
|---|---|---|
| 蒋天乐 | 设备/接口/路由对象、配置快照、ping 样本、故障事件和调用说明 | 公共标识、存储接口、调度入口、API 与错误格式 |
| 元泽瑞 | 设备与接口对应关系、SNMP 查询函数、ping 样本、可读 OID 范围 | 字节计数器等 OID 的批量读取需求，以及速率计算所需的元数据 |
| 段景瀚 | 设备清单、拓扑节点/关系、故障状态和页面字段 | 公共表格、状态标签、拓扑展示组件与页面约定 |

建议输出字段：设备使用 `device_id`；接口包含 `interface_id`、`device_id`、`if_index`；所有样本包含 `sampled_at`、数据来源和查询状态。ping 样本包含 RTT（ms）和丢包率（百分数）。具体格式由四人首次联调前确认。

SNMP 查询与错误解析由你统一维护；元泽瑞负责字节增量、速率和流量汇总算法。ping 采集由你维护，元泽瑞负责其性能趋势展示，避免同一批目标被重复无序探测。你的页面逻辑与接口处理由你完成，公共组件由段景瀚组织。

### 联调完成标准与验证

- [ ] 已记录 community 获取方式、可读 OID、接口索引和表遍历结果，共享材料不包含凭据。
- [ ] 设备与接口清单可入库、查询并在页面展示。
- [ ] 路由与拓扑关系可以解释来源，未知关系不会被展示为已确认事实。
- [ ] 两次配置快照可列出新增、缺失与变化。
- [ ] ping 和 SNMP 失败能区分，采集错误不会直接变成错误的宕机结论。
- [ ] 持续异常只形成一条活动事件，恢复后保存完整记录。
- [ ] 通过带标注的测试/回放数据验证异常与恢复逻辑，并与实时数据区分。
- [ ] 元泽瑞能按约定调用你的 SNMP 与 ping 输出，两个模块能一起运行。

真实停机或断链测试的允许方式需要向老师确认。初期可以验证规则和回放流程，但报告中要准确说明其数据来源。
